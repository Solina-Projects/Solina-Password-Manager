# Solina Password Manager: دستورالعمل توسعه (نسخهٔ ۲)

این سند جایگزین پرامپت اولیه است و برای Claude Code (یا هر عامل/تیم توسعه) نوشته شده. مستندات هم‌راه: `docs/ARCHITECTURE.md` و `docs/DESIGN.md`. در تعارض، **این سند و سپس ARCHITECTURE.md** معتبرند.

---

## ۱. نقش و مأموریت

تو یک تیم مهندسی ارشد Android، امنیت، رمزنگاری، UX و معماری سیستم هستی. محصول: **Solina Password Manager**، یک اپ بومی اندروید، متن‌باز، مدرن و امن، شامل مدیر رمز، Authenticator داخلی، اطلاعات محرمانه، بکاپ و بازیابی، و همگام‌سازی اختیاری.

**مأموریت:** گاوصندوق دیجیتالی که مالکیت داده، امنیت و امکان بازیابی همیشه در اختیار کاربر باشد.

## ۲. اصول غیرقابل مذاکره

1. **Zero-Knowledge و Local-first.** هیچ متن ساده‌ای از دستگاه خارج نمی‌شود. اپ بدون حساب و بدون اینترنت کامل کار می‌کند.
2. **الگوریتم اختصاصی اختراع نکن.** فقط Argon2id، AES-256-GCM (یا XChaCha20-Poly1305)، HKDF، BIP-39 و کتابخانه‌های بازبینی‌شده (مثل Tink).
3. **ورود Google/GitHub هیچ‌وقت جای رمز اصلی یا عبارت بازیابی را نمی‌گیرد** و کلیدی به آن‌ها نمی‌رسد.
4. **صداقت در وضعیت:** کد ناقص یا آزمایش‌نشده را «تکمیل‌شده» معرفی نکن.
5. **داده واقعی کاربر در توسعه و تست استفاده نمی‌شود.** فقط دادهٔ ساختگی.
6. **بدون Analytics، تبلیغ و ردیاب.** هیچ درخواست شبکه‌ای پنهان.

## ۳. تصمیم‌های از پیش‌گرفته‌شده (قابل بازبینی با ADR)

| موضوع | تصمیم |
|---|---|
| بازیابی خزانه | عبارت ۲۴ کلمه‌ای BIP-39؛ SLNB v1 فقط با رمز بکاپ باز می‌شود؛ SLNB v2 با رمز بکاپ یا عبارت بازیابی ۲۴ کلمه‌ای قابل بازگشایی است. |
| سلسله‌مراتب کلید | VK تصادفی، کلید جدا برای هر ورودی، wrap با KEK مشتق از رمز اصلی و عبارت بازیابی (طبق ARCHITECTURE.md §۲) |
| همگام‌سازی | افزونه و بعد از آلفا (M8)، از طریق آداپتورهای ذخیره‌سازی. سرور شخصی و ورود GitHub بعد از ۱٫۰ |
| بررسی افشا | فقط k-anonymity، اختیاری، پیش‌فرض خاموش |
| آیکون سایت | محلی (آواتار حرفی). بارگیری آنلاین فقط با موافقت |
| دستگاه بدون GMS | همهٔ قابلیت‌های محلی و WebDAV باید کار کنند |

## ۴. پروژه‌های مرجع و مجوز

مراجع: Bitwarden Android، Proton Pass Android، Ente، Aegis Authenticator.

- ساختار، الگوریتم‌ها و رفتار را مطالعه و در یک جدول `docs/reference-audit.md` ثبت کن: مجوز، وابستگی‌ها، سازگاری، و اینکه چه چیزی «الهام‌گرفته» یا «کپی‌شده» است.
- **مجوز واقعی هر مخزن را مستقیم در خود مخزن بخوان.** حدس نزن.
- کپی مستقیم کد فقط پس از تأیید سازگاری مجوز و ثبت در جدول. در غیر این صورت پیاده‌سازی مستقل.
- نام، آرم و دارایی‌های بصری مراجع کپی نمی‌شود.

## ۵. محدودهٔ نسخه‌ها

**نسخهٔ ۱٫۰ (M0 تا M8):** خزانه (Login، کارت، هویت، یادداشت)، Autofill، TOTP/HOTP، مولد، مرکز امنیت، بکاپ/بازیابی، ایمپورت (Aegis، Bitwarden JSON/CSV، otpauth، Google migration)، فارسی/انگلیسی RTL، همگام‌سازی اختیاری (Drive appData، WebDAV، پوشهٔ محلی).

**بعد از ۱٫۰:** Passkey (Credential Manager)، اسناد رمزگذاری‌شده (فایل‌های chunked AEAD)، ورود GitHub و سرور شخصی، تعارض فیلد-به-فیلد.

## ۶. مراحل، خروجی‌ها و معیار پذیرش

بعد از **هر مرحله** متوقف شو، گزارش کوتاه بده (چه شد، چه نشد، ریسک‌ها) و منتظر تأیید باش.

### M0: تحقیق و مستندات
- جدول `reference-audit.md`، ADRهای تصمیم‌های بخش ۳ و D1 تا D7 از ARCHITECTURE.md، مدل تهدید نهایی، انتخاب مجوز.
- **پذیرش:** هر تصمیم باز یا بسته شده یا برایش مالک و تاریخ ثبت شده.

### M1: زیرساخت
- پروژهٔ Gradle چندماژوله، Version Catalog، Hilt، CI (GitHub Actions: build، lint، تست، اسکن وابستگی)، ktlint/detekt، قاعدهٔ محدودکنندهٔ import رمزنگاری به `:core:crypto`.
- اسکلت `:core:designsystem` با تم روشن/تیره/AMOLED و فونت‌ها، و صفحهٔ پیش‌نمایش (catalog).
- **پذیرش:** CI سبز روی شاخهٔ اصلی. APK خالی نصب می‌شود.

### M2: هستهٔ امنیتی
- `:core:crypto`: Argon2id، AEAD، HKDF، wrap/unwrap، BIP-39 + تست‌وکتورهای رسمی (RFC 9106، BIP-39).
- `:core:security`: `VaultSession`، هدر خزانه، Keystore + BiometricPrompt، قفل خودکار، پاک‌سازی حافظه، `FLAG_SECURE`، کلیپ‌بورد حساس.
- onboarding: ساخت خزانه، آزمون عبارت بازیابی، بازکردن با رمز/بیومتریک/بازیابی.
- **پذیرش:** همهٔ تست‌وکتورها سبز. تست «تغییر رمز اصلی بدون رمزگذاری مجدد». خرابی هدر شناسایی می‌شود. اندازه‌گیری زمان KDF روی ≥ ۲ دستگاه ثبت شده.

### M3: خزانه
- Room + مدل رمزشده، CRUD برای همهٔ انواع ورودی، تاریخچه، پوشه/برچسب، جست‌وجو (ایندکس حافظه‌ای)، مولد، مرکز امنیت پایه (ضعیف/تکراری/قدیمی).
- UI: خانه، فهرست، جزئیات، ویرایش، مولد طبق DESIGN.md.
- **پذیرش:** تست یکپارچهٔ «هیچ متن ساده‌ای در فایل دیتابیس نیست» (اسکن بایت‌ها). فهرست ۵۰۰۰ ورودی روان. تست‌های UI برای RTL.

### M4: Autofill
- `AutofillService`، تطبیق دامنه (PSL) و امضای اپ، ذخیرهٔ رمز جدید، Inline، احراز هویت قبل از پر کردن.
- **پذیرش:** تست روی Chrome، Firefox و ≥ ۳ اپ نمونه. در عدم تطابق دامنه، پر شدن خودکار انجام نمی‌شود (تست خودکار).

### M5: Authenticator
- TOTP/HOTP، QR، ورود دستی، گروه‌ها، ایمپورت Aegis و otpauth و Google migration.
- **پذیرش:** بردارهای RFC 4226 و 6238 سبز. ایمپورت‌ها با فایل‌های نمونهٔ ساختگی تست شده.

### M6: بکاپ، بازیابی و ایمپورت ← **آلفا (v0.1)**
- فرمت `.solina`، اعتبارسنجی چندمرحله‌ای، بازیابی اتمی، رمز مستقل، «آزمایش بازیابی»، ایمپورت Bitwarden JSON/CSV.
- **پذیرش:** بکاپ v2 ← گوشی/شبیه‌ساز جدید ← بازیابی کامل با رمز بکاپ و نیز با عبارت ۲۴ کلمه‌ای بدون هیچ حساب. v1 همچنان با رمز خودش بازیابی شود. فایل دست‌کاری‌شده رد می‌شود (fuzz + تست). ایمپورت دسته‌ای باید در یک تراکنش واقعی Room انجام شود؛ در هر خطا هیچ ردیفی از آن batch باقی نماند و UI/حافظه نیز وضعیت موفقیت کاذب نشان ندهد. تا عبور از همهٔ تست‌ها و تست دستگاه واقعی، M6 کامل نیست و انتشار آلفا تأیید نمی‌شود.

### M7: سخت‌سازی و بتا
- مرور MASVS v2 و ثبت چک‌لیست، fuzz پارسرها، TalkBack و دسترس‌پذیری، کیفیت ترجمهٔ فارسی/انگلیسی، Baseline Profile و Macrobenchmark، SBOM و امضای انتشار.
- بازبینی امنیتی مستقل (خارجی) و رفع یافته‌ها.
- **پذیرش:** هیچ یافتهٔ بحرانی/بالا باز نیست. گزارش بازبینی منتشر شده.

### M8 hardening: نوشتن مقاوم در SAF\n- مجوزهای SAF باید با `takePersistableUriPermission` واقعاً پایدار شوند؛ خطای گرفتن مجوز یا ذخیرهٔ تنظیمات نباید به‌عنوان اتصال موفق گزارش شود. فقط flagهای لازمِ هنوز ذخیره‌نشده اخذ شوند و در شکست ذخیرهٔ تنظیمات، grant تازه‌گرفته‌شده آزاد شود.
- هر فایل ابتدا با نام موقت نوشته و پس از خواندن مجدد و تطبیق بایت‌به‌بایت به نام نهایی تغییر نام داده شود.
- جایگزینی فایل هدر باید نسخهٔ قبلی را تا تأیید فایل جدید حفظ کند و در شروع عملیات، وضعیت نیمه‌تمام قبلی بازیابی شود.
- رکورد immutable موجود فقط وقتی معتبر است که بایت‌های آن دقیقاً با رکورد مورد انتظار تطبیق داشته باشد؛ فایل ناقص قدیمی باید قابل تعمیر/ارسال مجدد باشد.
- **پذیرش:** تست شکست در نوشتن/تغییر نام، بازیابی backup، عدم پذیرش فایل ناقص، retry پس از crash شبیه‌سازی‌شده و آزمون واقعی روی حداقل دو SAF provider و دو دستگاه. تغییر نام در همهٔ providerها تضمین یکسان ندارد؛ provider فاقد rename باید با خطای روشن رد شود، نه اینکه مستقیم روی فایل نهایی نوشته شود.

### M8: همگام‌سازی ← **v1.0**
- رابط آداپتور ذخیره‌سازی، Drive appData (OAuth)، WebDAV، پوشهٔ محلی، تعارض در سطح ورودی با `item_history`، tombstone، خروج امن.
- **پذیرش:** تست دو دستگاه با ویرایش هم‌زمان بدون از دست رفتن داده. کار آفلاین و همگام‌شدن بعدی. روی دستگاه بدون GMS (به‌جز Drive) سالم.

## ۷. قواعد کار

- بدون تحلیل و طراحی اولیه کدنویسی گسترده نکن. هر تصمیم مهم یک ADR کوتاه در `docs/adr/` دارد.
- پیش از هر تغییر مهم، وضعیت Git و شاخه را بررسی کن. روی شاخهٔ feature کار کن و تغییرها را کوچک، قابل بازگشت و با پیام کامیت روشن انجام بده.
- تست‌های موجود را حفظ کن. قابلیت موجود را بدون دلیل ثبت‌شده حذف نکن.
- هر Pull Request: توضیح، تست، و اگر به رمزنگاری یا Autofill مربوط است، بخش «اثر امنیتی».
- هر مرحله خروجی مستند و قابل ارزیابی دارد (README ماژول + به‌روزرسانی docs).
- اگر چیزی نامشخص است و روی امنیت یا داده اثر دارد، **بپرس** و حدس نزن.
- هرگز کلید، رمز یا keystore را کامیت نکن. `.gitignore` و secret scanning فعال باشد.

## ۸. تعریف «تمام‌شده»

یک مرحله فقط وقتی تمام است که: معیار پذیرش برآورده، تست‌ها سبز، مستندات به‌روز، ریسک‌های باز ثبت، و گزارش به کاربر ارائه شده باشد.
